# 管理者用ページ：公開前の確認

## 用意した画面
- ホーム最下部の小さな「管理者用」リンク → `/admin/`。
- 管理者メールアドレス＋パスワードでログイン。一般の同期ID・PINとは別。
- 期間、ゲーム、同期ID・名前・匿名IDで絞り込み。
- ゲームを開いた回数、操作時間の推定、対応ゲームの解答数・正解率、利用日数。
- 未登録者は匿名の端末別。別端末の同一人物を特定する機能ではない。

## テスト・診断
- ログボを6日連続・100ジェムから試す画面。
- 受取、翌日、同期、別端末を再現、初期状態へのリセット。
- 本番のタスクバーとログボ画面のコードを読み込む。
- iframeを別の保存領域に隔離し、実際の残高・PIN・受取履歴を読み書きしない。外部通信はCSPで禁止。
- 実際のアカウントは、連続日数・受取済みフラグ・獲得イベントの有無だけを管理者が読み取りで診断。
- 補填ボタンや本番の日付変更・ジェム操作はない。

## 集計の範囲と保存
- 新機能公開後の記録が対象。過去の利用時間・未登録者の利用は遡れない。
- ページを開いた回数はゲーム完了回数ではない。
- 操作時間は、画面が表示され直近60秒に操作があった時間の推定。
- 解答数は実績イベント対応ゲームのみ。
- 5分ごとの変化分とページ離脱時に送信。再送は同一セッション行に単調マージ。
- 保存対象は原則90日、50,000行を上限。古い行は新しいセッション保存時に削除。
- 新しい有料サービス、課金設定、定期ジョブは追加しない。既存Supabaseの容量・実行枠を使用。

## サーバー側
- 新規テーブル `sushi_admin_users`、`sushi_usage_sessions`。
- 新規RPC `sushi_record_usage`、`sushi_usage_report`。
- すべてRLS有効。匿名・通常ログイン利用者は表・RPCを直接読めない。
- `usage-admin` はSupabase Authのトークンを検証し、管理者名簿で権限確認してから集計を読む。
- `usage-record` は未登録者の記録だけ。同期IDを指定して他人に紐付けることはできない。
- 登録者の記録は `sushi-id-sync` の既存PIN確認を経由し、サーバーが同期IDを決める。
- 閲覧応答はno-store。トークンとパスワードはブラウザの保存領域に置かず、再読み込みでログインが必要。15分でログアウト。

## 公開手順（本番DB変更の許可後）
1. `supabase/sql/admin-usage.sql` のテーブル2件・RPC2件を本番へ適用。
2. `usage-record` をverify_jwt=false、`usage-admin` をverify_jwt=trueで公開。sushi-id-syncの認証済み記録ルートを更新。
3. 管理者用のSupabase Authアカウントを作り、そのUUIDだけを `sushi_admin_users` に登録。
4. 管理者のパスワード設定は設定リンク等で本人が行う。チャットでパスワードを受け取らない。
5. 正常な管理者ログイン、一般利用者拒否、ゲストと同期ID記録、ログボのテスト隔離を本番でも確認。
6. PRをマージし、PWAキャッシュを更新。

現在は本番DBを変更していない。公開と管理者アカウント登録は、DB変更の明示的な許可を受けてから行う。
