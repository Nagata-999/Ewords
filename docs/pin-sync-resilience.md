# PIN同期の障害耐性（2026-10-22）

## 対象と処理経路

PINの接続・同期は `shared/sushi-profile.js`。`sushigacha/site-taskbar.js` が順に同期モジュールを読み込む。通常のプロフィール同期は送信と取得が別APIではなく、`sushi-id-sync` の `sync` にローカル状態をPOSTし、保存された統合結果を同じレスポンスで取得する。

|データ|ローカル保存と同期|
|---|---|
|学習履歴・苦手単語|`shared/learning.js`。`sushitan_learning_v1:event:<id>` が原本。苦手状態はイベントから再計算。辞書カードは同prefixの`card:<word_id>`。サーバー `mergeLearning` はIDの和集合、旧インポートIDは最大回数・時刻を保持|
|ジェム・取得アバター・ログボ・日課|`sushitan_login_bonus_v1`。`gem-system.js` 等が保存。未確認の加減算は`gemPendingEvents`、表示用履歴は`gemEvents`。サーバー `mergeLedger` はイベントIDの重複を除き、サーバー残高に未処理の増減だけを適用|
|アバター|所有アイテムは和集合。現在の着せ替えは既存仕様どおり端末の設定を保持。性格設定は更新日時による既存統合を維持|
|実績|`achievement-ledger.js` の `sushitan_achievement_v2:event:<id>`。`achievement-transport.js` と `achievement-sync-bridge.js` がページ単位で送受信し、確認済みID・形式・ページ継続を検証|
|解答結果|`sushitan_achievement_outcome_v1:<id>`。プロフィール同期後に `outcome_sync` で200件単位の送信・取得|
|実績報酬|PIN確認後の既存RPCによる受取と、サーバーの残高スナップショットを使用。クライアントで報酬を再加算しない。受取証はアカウント別の既存キーに保持|
|ログイン実績|`achievement-login.js` の別系統 `login_visit`。15秒期限、同時実行防止、成功後だけ当該時間の確認済み状態を更新する既存動作を維持|

`supabase/functions/sushi-id-sync/index.ts` のPIN認証、保存比較RPC `sushi_save_profile_if_current`、最大5回の競合再試行は変更していない。DB・テーブル・RLS・課金設定の変更はない。

## 修正

- HTTP失敗、15秒の期限超過（応答本文の停滞を含む）、null、不正JSON、未確認データを空状態に変換せず失敗させる。
- `ok`、アカウント、残高・イベント・学習形式、送信イベントの確認を保存前に検証する。不正なローカルJSONも空に置き換えない。
- ローカルへの変更を準備してから保存。`sushitan_sync_journal_v1` に保存前後の値を先に記録し、途中失敗時に元へ戻す。次の試行では中断された記録を回復する。後から書き換えられた値は復元で上書きしない。
- 未同期フラグ `sushitan_sync_pending_v1` を送信前に永続化。プロフィール・解答結果・利用可能な実績同期が成功し、途中の新規変更もない場合だけ解除する。学習・ジェムの原データは送信後も保持する。
- 同期Promiseを共有し、ウォレット変更を直列化。Web Locks対応環境では同期のウォレット処理を同一オリジンのタブ間でも直列化する。受取・受取証取得も多重実行を抑止する。
- 自動同期失敗後は自動試行を停止し、手動同期・接続復旧で再試行する。ページを閉じる時に完了を期待する送信をしない。ページ数の上限到達も成功扱いしない。
- 解答結果の保存失敗を握りつぶさず、全体を未同期にする。サーバー応答の検証前に実績基準値を変更しない。
- 元のデータ形式を維持。新しい補助キー2つのみ追加。管理者機能の封印は維持。

## 最小検証

## 残る制約

- この検証範囲では通信失敗によるデータ消失は再現せず、修正後の保持・再同期を確認した。ブラウザーデータの手動削除、端末故障、保存領域自体の喪失まで保証するものではない。
- ストレージ容量不足の場合、保存前の復元用記録も作れず同期を中止することがある。既存データは残すが、容量不足のまま新規学習の永続保存を保証できない。復元自体が失敗した場合も復元記録を残して次の同期を中止・再試行する。
- 複数タブでゲーム自体が同じlocalStorageオブジェクトを同時に更新する既存処理全体はトランザクション化していない。今回のタブ間ロックは同期のウォレット処理に適用する。
- 2端末のオフライン支出が合計残高を超えるケースは、既存のサーバー計算（各イベントを一度だけ反映、最終残高は0以上）を維持する。新しい金融台帳や支出予約方式には変更していない。
- 既存のサーバーが拒否する旧イベントがある場合は、成功と偽らず未同期を残す。同期完了にはその原因の個別確認が必要となる場合がある。
- サーバー確認が必要なログイン実績は、オフライン期間を遡って確定する仕様には変更していない。既存履歴を消さないことと、未確認の報酬を付けないことを優先している。
- 全ゲーム・全ブラウザー・全既存テストの網羅試験は今回実施していない。

参照：[Supabase Edge FunctionsのHTTPステータス](https://supabase.com/docs/guides/functions/status-codes)。402に限らず非成功応答を失敗として扱う実装で、特定の無料枠停止条件への依存を避けている。
