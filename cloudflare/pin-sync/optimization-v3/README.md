# 実績同期のDB読み取り削減（本番未適用）

## 状態

2026-11-09: 実装候補とオフライン検証を保存。本番D1への問い合わせ、マイグレーション、ゲームを使った試験は実行していません。
Cloudflareで直接編集された最新Worker全体はGitHub mainと一致しません。このディレクトリの古い基底コードを本番Workerへ丸ごと上書きしないでください。
`backend.patch` は保存済みコードに対する変更差分です。本番の対象関数を確認して差分だけを取り込みます。認証・ランキング・ルーティングを置換しません。

## 実装

1. `PIN_SYNC_OPTIMIZED=true` の場合、実績保存前後のSELECTを省略。DBトリガーが同じIDの内容矛盾を拒否し、1つのINSERT文全体を取り消します。旧方式・学習outcomeの保存は維持。
2. サーバー連番を持つ追記専用feedから差分取得。日時やevent_idの大小に依存せず、遅れて届いた他端末の記録も取得できます。端末保存に成功したページだけカーソルを更新。旧クライアント・旧サーバーも利用可能です。
3. 全正解数、単語ゲーム正解数、TOEIC正解数、1日のゲーム種類数の最大値を、新規記録と同じDBトランザクションで更新。該当する実績判定を1行の読み取りに変更。履歴は削除しません。順序に依存するコンボ・復習等の判定は変更しません。

クライアントの`transport.js`はPagesの`sushigacha/achievement-transport.js`、`bridge.js`はWorkerの`pin-auth-poc/assets/bridge.txt`へ対応します。Worker内のPIN認証用transport.txtとは別です。

## 検証

`node --test offline.test.mjs`（Node 24）。SQLiteの`:memory:`のみ使用し、ネットワークもD1バインディングも使いません。6件成功。
重複、矛盾時のバッチ全体の取り消し、旧方式、別アカウント、JST日付、通信失敗、端末保存失敗、差分再開、100件以下の分割移行を確認しています。これはD1本番の実行計画・使用量の測定ではありません。

## 授業を止めない導入順序

1. Cloudflareの現行コードへ差分を照合し、既存の直接編集を保持。環境変数`PIN_SYNC_OPTIMIZED`は未設定またはfalseのままにします。
2. 授業外かつ読み取り・書き込み枠に余裕がある時間に、`pin-sync/event-optimization.sql`を一度適用。テーブルとトリガーの作成のみで、全履歴の一括移行はしません。
3. `backfillEventBatch(DB,100)`を管理作業として明示的に実行。1回最大100件、繰り返しの自動ループなし。戻り値のmetaで実消費を確認し、必要なら小さい件数へ下げます。進捗は同一トランザクションで保存され、中断・再開できます。ゲームやログイン処理から呼びません。
4. 戻り値の`progress.complete===1`を確認してから新方式を有効にします。移行途中では絶対に有効化しません。完了後は旧クライアントからの新規記録もトリガーで反映されます。
5. クライアント2ファイルを反映。初めての差分同期は履歴全体を取得し、次回から追加分だけになります。全端末の一斉リロードを求めず、自然な再読み込みで更新します。

## 消費量と戻し方

読み取り削減と引き換えに、初回移行・新規イベント時の書き込みと保存容量は増えます。100件の移行は100行の書き込みという意味ではありません。インデックス・集計更新分もあるため、日次書き込み枠も確認します。実測の削減率はまだありません。
問題があれば`PIN_SYNC_OPTIMIZED=false`で従来の読み取り方式に戻します。トリガーによる集計更新は継続します。トリガー自体に問題がある場合は旧コードへ戻した上で対象トリガーを停止し、再有効化前に整合性を再構築します。
feedの連番を初期化・再作成しないでください。端末カーソルとの対応が失われます。元履歴のUPDATE/DELETEは禁止トリガーで拒否します。将来のアカウント削除機能には、関連データとカーソルを含む専用の削除設計が必要です。
